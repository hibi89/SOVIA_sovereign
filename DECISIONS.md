# Architecture decision log
Updated 2026-10-25 KST

## ADR-001: Unified core vs two separate products
Option A independent Cloud and Private codebases: quickest naive start per product but duplicate tests, bugs, costs and inconsistent policy decisions.
Option B common SOVIA Core with deployment-specific adapters: small up-front abstraction cost, better consistency and maintenance; Private remains distinct in packaging/security acceptance.
Decision: **B**, as directed in the product discussion. No separate cloud/private forks.

## ADR-002: Audit after execution vs inline traffic interception
Option A deterministic post-event audit of supported logs: low cost, safe read-only pilot, easier tests; cannot stop malicious actions in real time.
Option B inline runtime prevention gateway: potentially higher value; introduces critical-path latency, vendor/SDK integrations, outages and legal liability.
Decision: **A for MVP**, B as a conditional expansion after customer validation and explicit owner approval.

## ADR-003: Build cloud first vs local-first
A Cloud-first: easy subscription demo, but requires production data governance, hosting, tenant isolation and spend before paying customers.
B Local-first: near-zero cash, works in sensitive environments, reduced liability from central raw data; later connectors and hosted deployment require engineering work.
Decision: **B**, with canonical schema and dependency injection to avoid rewrite for Cloud.

## ADR-004: Persistent monitoring vs human-managed SOC
A Human-operated monitoring for every customer: service-heavy cost grows with accounts and requires emergency staffing.
B Product-led automatic policy monitoring with bounded enterprise support: low unit cost, scales better but needs trustworthy notification and documented limitations.
Decision: **B**; no 24/7 operator promise.

## ADR-005: Customer data collection
A Central full prompt/document capture maximizes observability but privacy, consent and cost risk high.
B Structured metadata by default, optional user-approved redacted evidence: limited visibility but lower costs, defensible privacy posture.
Decision: **B**. Findings must declare observability limits.

## ADR-006: 72-hour runnable MVP-first delivery (approved 2026-10-26)
A. Fully implement architecture and comprehensive assurance before demo: lower risk of later rework but slower to validate core value and delays customer discovery.
B. Build demonstrable vertical slice in 72 hours, run basic safety tests continuously, track blueprint gaps and finish market-facing product requirements before first sale: fastest feedback and lowest cash use; requires disciplined gap ledger to avoid shipping incomplete security claims.
Decision **B**, as owner requested. Key restriction: advanced hardening may be postponed, but input/data protection and actual smoke/unit tests cannot. Marketing collateral is drafted concurrently, not falsely published as finished product.

## ADR-007: P2 CSV export path (2026-10-26)
Alternative A: stdlib csv.writer, fixed findings+events columns, Excel-compatible UTF-8 BOM, explicit CRLF, guarded formula-like values, no third-party install. Low execution cost and good portability, but output remains text-only and spreadsheet behavior varies by import mode.
Alternative B: pandas + openpyxl XLSX export. Rich typed tabs/formatting and safer display control in compatible Excel, but dependency footprint, install time, test matrix and maintenance cost increase for a small offline MVP.
Decision: **A for first P2 milestone**, already tested with synthetic data (54 unit tests; commit 6b3be7a4512049caa5a329776e2a63462cd6c8fa). Add XLSX only on evidence of customer demand. CSV export is not source CSV ingestion; maintain separate gap. Escaping leading = + - @ with apostrophe reduces common formula injection but is NOT a guaranteed cross-application security boundary. No production/customer claim.


## ADR-008: P2 PDF authoring with Korean typography (2026-10-26)
Option A: Rely on local browser print-to-PDF from existing HTML. No Python dependency, quick manual workaround, but unattended PDF generation depends on a supported browser, print flags and OS automation with inconsistent results.
Option B: Make PDF an **opt-in** `--pdf-output` using free ReportLab 4.x and a locally installed Korean TrueType font. Deterministic, printable file generated by the existing CLI, with extra one-time dependency/font compatibility work. Base HTML/JSON/CSV remains stdlib-only.
Decision: **B** for automatic PDF export; A is manual fallback if install/TTF platform gate fails. Never vendor/supply standalone font files. Synthetic 66 tests passed, one A4 PDF inspected, 115 events generated 6 pages with no clipped extracted text; source commit e2ffa99485b57d1e07d6b1ac119226fb86b045ed. Fresh Windows install, real customer output and commercial data processing remain unverified.


## ADR-009: P2 CSV source import before persistent SQLite (2026-10-26)
A. Add strict canonical metadata CSV source with a JSON policy file: small stdlib implementation, no persistence/new costs, immediately extends usable import formats and reuses existing evaluator/report tests; still cannot safely assume n8n/customer CSV formats.
B. Build SQLite history/dedup first: improves recurrent audits and reliability but introduces migrations, backup/delete, storage of sensitive metadata and corruption recovery before the simple source format is available.
Decision: A for v0.6 synthetic-only. Restrict unknown columns and explicit boolean permissions, same 1MiB/1000-event envelope, never store raw prompts, no offline outbound network dependency; use B as next P2 milestone with tests for idempotency/collision/backup/restore/purge. GitHub Actions Python 3.11/3.13 92 discovered / 82 executed passing / 10 optional PDF skipped each (run 40212874275). Real customer CSV layouts require authorized sanitized adapter later.


## ADR-010: Opt-in local history storage — SQLite vs append-only JSONL (2026-10-26)
A: JSONL append logs are easy to inspect and have no schema initialization, but crash recovery, cross-file deduplication, referential deletion and consistent snapshot/restore demand substantial custom code; they also risk inadvertently preserving unredacted source fields.
B: Built-in sqlite3 supports unique keys/foreign keys, atomic writes, integrity checks, secure_delete/VACUUM and the SQLite backup API with zero network/third-party dependency, at the cost of extra schema/migration work and sensitive-data retention risk.
Decision B **only for opt-in synthetic metadata history**, not default audit execution. Store hashed identifiers/content and bounded rule metadata, never original prompt or event labels. Each import transactional, no-clobber backup/restore, explicit delete confirmation and version 1 gate; no automatic retention or future migration. Hashes may enable dictionary/linkage; no anonymity claim. Initial Windows backup/fsync and handle-close regressions corrected and validated in CI 40214522381. P2 commercial retention/privacy acceptance remains open.
